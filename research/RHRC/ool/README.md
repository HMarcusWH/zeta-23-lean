# OoL-MVS RH integration

Claim firewall: **RH and Step 4 remain OPEN.**

## Current entry point

The active [OOL_REFERENCE.json](OOL_REFERENCE.json) records the OoL-MVS 2.7.7
domain-neutral governance subset. Start with the
[framework and engine map](../../../docs/FRAMEWORKS.md) and the
[integration boundary](../integration/INTEGRATION_BOUNDARY.json).

[semantics.py](semantics.py) preserves Strong Kleene `PASS`/`FAIL`/`NA` evidence
logic: missing or unresolved support stays unresolved. Quantified absence claims
require complete enumeration of the exact route scope. Confirmatory execution
requires frozen route and boundary digests, continuous provenance and qualified
interfaces using actual outputs. Independent module success alone does not close
an end-to-end route.

The [evidence types](v277_evidence.py), [threshold rules](v277_thresholds.py) and
[authority adapter](v277_authority.py) keep claim results separate from certificate
status. Certificates default to `INCOMPLETE` without independently configured
policy and reviewed signatures. `VALID` authenticates a reviewed binding; it
does not establish physical or mathematical truth. The repository does not import
the origin-of-life physical claims, laboratory qualification or the complete
canonical 24-claim runtime as RH premises.

The [OPICA adapter](opica_composition.py) checks exact expected interfaces,
source/context/witness identity, phase agreement and replayed binding receipts.
Different producer and consumer objects require a proved transport. It rejects
unauthorized premises, open obligations treated as proofs and circular routes.
The [governed service](../integration/opica_composition/service.py) obtains its
interface ports from the independently checked native dependent proof packet.

The active atlas uses [rhkg_phase_atlas_v2.json](configs/rhkg_phase_atlas_v2.json)
and [rhkg_phase_atlas.py](rhkg_phase_atlas.py). Read the
[generated report](generated/RHKG_OOL_PHASE_ATLAS.json) and
[route contacts](generated/RHKG_OOL_ROUTE_CONTACTS.jsonl) for source-bound counts
and dispositions. Atlas contact remains a discovery lead requiring a new exact
Lean theorem attempt.

## Historical v2.7.6 / post-#265 Phase Atlas snapshot

The following describes the initial integration snapshot. Its version and counts
are historical, not the current inventory. The initial repository import used
OoL-MVS v2.7.6 for domain-neutral operational semantics; the preserved reference
is [OOL_REFERENCE_v2_7_6.json](OOL_REFERENCE_v2_7_6.json).

The post-#265 adapter does **not** treat a theorem module, type hash, graph
neighbourhood, or FFBBP cohort as a mathematical handoff. It takes the exact
680 `SOURCE_ONLY_PUBLIC_THEOREM` Lean declarations and extracts a separate
DISCOVERY_ONLY compiler dependency closure rooted at those declarations.

The first Phase Atlas intentionally uses the existing
`THEOREM_VALUE_ERASED_SUPPORT` projection:

- theorem proof-body VALUE edges are erased;
- TYPE and STRUCTURE edges remain;
- VALUE edges of non-theorem support declarations remain;
- only local `Zeta23.*` declaration contacts are used for interface
  classification.

Three disjoint registered-claim anchor families defined that snapshot's research
interfaces: carrier/spectrum, aperture/arithmetic, and ground/source. Support
shared by multiple families is removed before a contact can count as
interface-distinctive. This prevents generic common infrastructure from
manufacturing a fake cross-interface signal.

The atlas separately checks contact with the exact #261 theorem-value-erased
21-edge arithmetic frontier. Such contact is a **LEAD / discovery surface**,
not theorem composition and not RH evidence.
